TipsyTheoryy Production Readiness Implementation Plan
======================================================

Document purpose
----------------
This plan converts the current TipsyTheoryy backend, Flutter customer app,
and merchant web panel into a production-ready SaaS payment platform.

Repositories in scope
---------------------
- Backend: C:\Users\PC\Desktop\tipsytheoryy
- Flutter app: C:\Users\PC\Desktop\tipsytheoryy_app
- Merchant panel: C:\Users\PC\Desktop\tipsytheoryy_merchant

Primary production risks identified
------------------------------------
1. Payment confirmation has two active implementations.
2. select_for_update() is used outside transaction.atomic() in the unified
   confirmation service.
3. Retry payment can send an STK push synchronously and queue another STK push.
4. Payment idempotency is mostly cache/application based, not database based.
5. Payment audit records do not correctly cover subscriptions and all payment
   domains.
6. Callback processing can acknowledge HTTP success without durable ingestion.
7. Wallet and loyalty mutations are not implemented as financial ledgers.
8. Overpayments, refunds, reversals, and manual review are not first-class
   states.
9. Flutter and merchant clients depend on checkout_request_id instead of a
   stable application payment identifier.
10. DEBUG defaults to True and SQLite/localhost Redis are possible fallbacks.
11. Payment callback, concurrency, reconciliation, and failure tests are
    largely absent.

Production principles
---------------------
- The backend is the source of truth for payment state and amounts.
- Every provider event is durably recorded before acknowledgement.
- Every payment state transition is atomic and auditable.
- Every business side effect is exactly-once or safely idempotent.
- Provider checkout IDs and receipts are unique where present.
- No payment remains pending indefinitely without alerting or manual review.
- Customer and merchant clients never infer payment success from UI events.
- External notifications never run while payment database locks are held.

Target payment lifecycle
------------------------

INITIATION_REQUESTED
        |
        v
PAYMENT_ATTEMPT_CREATED
        |
        v
STK_REQUEST_SENT ---- provider/network failure ----> INITIATION_FAILED
        |
        v
PENDING
   |       |        |          |
   |       |        |          +--> MANUAL_REVIEW
   |       |        +-------------> EXPIRED
   |       +----------------------> FAILED
   +------------------------------> CONFIRMED

CONFIRMED may emit downstream events for order fulfilment, subscription
activation, wallet/loyalty accounting, notifications, and analytics.

Phase 2 - One authoritative payment service
--------------------------------------------
Objective: eliminate divergent confirmation behavior.

Tasks:
- Make one service the only authority for payment state transitions.
- Route callbacks, STK queries, reconciliation, and admin actions through it.
- Remove duplicate confirmation behavior from views.py after migration.
- Put record lookup, select_for_update(), validation, state transition, and
  financial effects inside one transaction.atomic() block.
- Lock PaymentAttempt first, then lock its business target.
- Re-read all records after acquiring locks.
- Reject already terminal attempts as idempotent no-ops.
- Reject callbacks for a different checkout ID or business target.
- Validate provider, amount, currency, phone where applicable, and receipt.
- Reject underpayments.
- Route overpayments to OVERPAID or REFUND_REQUIRED; never silently accept.
- Record every state transition with actor/source and timestamp.
- Use Decimal for every amount calculation.

Order confirmation must atomically:
- Mark PaymentAttempt confirmed.
- Mark the order paid.
- Record receipt and payment completion time.
- Create exactly one order-paid ledger event.
- Reserve or deduct inventory according to the final inventory policy.
- Clear only the relevant cart/order items.
- Award loyalty through an idempotent loyalty ledger.

Subscription confirmation must atomically:
- Mark the PaymentAttempt confirmed.
- Mark SubscriptionPayment successful.
- Activate the correct store plan.
- Extend the subscription from the correct business date.
- Record the receipt in the subscription payment audit trail.

Shiriki confirmation must atomically:
- Lock the Shiriki session.
- Lock the contribution.
- Calculate remaining capacity from applied amounts.
- Record amount applied and overflow separately.
- Credit overflow through a wallet ledger.
- Award loyalty once through a loyalty ledger.
- Complete the session only when the applied amount reaches the target.

Exit criteria:
- There is one production confirmation path.
- Duplicate confirmation has no duplicate side effects.
- Concurrent confirmation tests pass.
- Subscription, order, and Shiriki audit records are complete.

Phase 3 - Idempotent payment initiation
----------------------------------------
Objective: prevent duplicate STK prompts and duplicate payment attempts.

Backend tasks:
- Accept an Idempotency-Key header or request field.
- Atomically find or create a PaymentAttempt for the key.
- Return the existing active attempt for repeated requests.
- Create the payment attempt before calling Safaricom.
- Persist the checkout request ID immediately after successful initiation.
- Never send an STK push from both an HTTP request and a Celery task.
- Remove the current retry flow that sends one synchronous request and then
  queues another STK task.
- Make the Celery task process only one identified PaymentAttempt.
- Add task-level locking using the database, not only Redis.
- Return stable payment_id, status, amount, and retry metadata to clients.

Recommended response:
{
  "payment_id": "pay_123",
  "status": "pending",
  "checkout_request_id": "ws_CO...",
  "amount": "3000.00",
  "next_poll_after_seconds": 3
}

Exit criteria:
- Repeated requests with the same idempotency key create one attempt.
- Concurrent requests produce one STK push.
- A client timeout does not cause a second STK push automatically.

Phase 4 - Durable callback ingestion
-------------------------------------
Objective: prevent lost callbacks and decouple Safaricom from processing.

Callback endpoint:
- Validate HTTP method and JSON structure.
- Validate trusted proxy and callback source configuration.
- Do not trust an arbitrary first X-Forwarded-For value.
- Hash and persist the raw callback in CallbackInbox.
- Return HTTP 200 only after durable persistence succeeds.
- Return a retryable non-2xx response if persistence fails.
- Do not call notification, email, or reconciliation code in the endpoint.

Callback processor:
- Claim one inbox event using a database lock.
- Match by checkout_request_id and provider.
- Process through the authoritative payment service.
- Retry transient database/provider errors.
- Move unmatched events to UNMATCHED or MANUAL_REVIEW.
- Preserve the raw callback permanently according to retention policy.
- Make duplicate event hashes safe no-ops.

Exit criteria:
- A callback can be recovered after worker, Redis, or database interruption.
- No callback is acknowledged and discarded.
- Duplicate callbacks do not duplicate financial effects.

Phase 7 - Reconciliation and recovery
--------------------------------------
Objective: survive lost callbacks, provider delays, and worker outages.

Tasks:
- Reconcile PaymentAttempts in PENDING after a configurable delay.
- Lock attempts before reconciliation.
- Query Safaricom status using the correct merchant credentials.
- Submit the result to the same confirmation service used by callbacks.
- Record each reconciliation attempt and result.
- Stop automatic retries after a controlled limit.
- Move unresolved records to MANUAL_REVIEW.
- Create alerts for payments pending beyond SLA.
- Add operator tools to inspect, retry, confirm, refund, or annotate records.
- Never use fabricated receipts such as RECONCILED as provider receipts.

Recommended operating thresholds:
- First reconciliation: 2-3 minutes after initiation.
- Subsequent reconciliation: exponential backoff.
- Manual review: after 30-60 minutes, depending on provider behavior.
- Alert: payment pending beyond configured business SLA.

Exit criteria:
- Lost callbacks are recovered automatically.
- Reconciliation workers can run concurrently without duplicate processing.
- Operators can resolve unmatched and ambiguous payments.

Implemented:
